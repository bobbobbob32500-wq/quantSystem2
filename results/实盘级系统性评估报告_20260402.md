# 量化系统实盘级系统性评估报告（2026-04-02）

> 评估目标：对 `d:/HuaweiAI/quantSystem2` 量化交易辅助系统进行全面、系统性评估，判断是否达到“实盘级”水准，并输出问题清单、风险评估与优化建议。  
> 评估原则：**证据优先**（日志/数据库快照/测试结果/配置与代码实现），定量+定性结合，结论可复验。

## 一、总体结论（是否达到实盘级）

【结论 / 方案】  
**当前系统“接近实盘可用”，但尚未达到严格意义的“实盘级（可长期无人值守稳定运行、可审计、可回滚、可量化 SLA）”。**  
核心原因是：  
- **可复现的逻辑一致性问题仍存在**：`pytest` 全量执行结果 **8 处失败**（124 通过 / 86 跳过 / 8 失败），其中包含二次启动盘中信号阈值、系统完整性保护、市场分析依赖表结构等关键链路。  
- **稳定性存在硬风险**：运行监控快照显示 `service.monitor_check` **P95 时延约 97 秒**，对盘中信号“及时性”和“服务主循环稳定性”构成高风险。  
- **安全合规存在致命隐患**：`src/config/config.yaml` 明文包含 `tushare_token` 与企业微信 webhook（属于凭据泄露）。  

因此：**建议将系统定位为“准实盘/半自动辅助”是合理的；若要升格为实盘级，需要做一轮工程化加固与一致性修复。**

## 三、系统稳定性评估

### 3.1 负载与运行状态（正常/峰值/极限）

【结论 / 方案】  
系统具备**健康监控框架**（心跳、事件分级、时延统计、告警冷却、快照落库），但当前指标提示：**盘中监控一次轮询的尾部时延过高**，在峰值/极限负载下可能出现“信号延迟、主循环阻塞、推送堆积、数据源超时导致连锁降级”。

【定量证据】（近 24 小时，来自 `quant_system.db`）  
- **健康快照数量**：`health_snapshot` 总计 396 条；近 24h 统计到 395 条，来源均为 `service`  
- **主循环延迟**：`service.main_loop` 平均约 **1000ms**，P95 约 **1000.8ms**（符合“每秒心跳”设计）  
- **监控轮询延迟（关键）**：`service.monitor_check` 的 **P95 ≈ 97349ms（约 97 秒）**  
  - 解释：监控轮询内部包含分钟线/实时行情/行业确认/评分/风控等多步骤，任何外部数据源抖动都会把尾部时延拉大  

【风险评估】  
- **高风险**：97 秒级 P95 直接破坏“盘中买点推送及时性”，也会造成主服务的“可预期性”下降（卡顿/错过窗口/推送滞后）。  
- **中风险**：`component_status` 里 `service.lifecycle / scheduler_startup / monitor_startup` 仅在启动时记录，之后不再心跳更新，会被标记为 `stale`，导致健康面板“误报不健康”，影响运维决策。  

【优化建议（落地）】  
- **将 `monitor_check` 拆成“可超时/可并发/可降级”的阶段管道**：  
  - 设置“单轮最大耗时预算”（例如 3~5 秒），超时则降级使用缓存/减少标的数/跳过行业确认  
  - 对分钟线拉取启用硬超时 + 失败快速返回，避免尾部拖垮  
- **对关键组件补齐周期性心跳**：例如每 N 秒对 `service.lifecycle` 写一次 `record_success` 或专门 heartbeat，避免状态长期 stale  
- **建立压测场景**：以“候选池数量×分钟源延迟×并发 workers”形成 3 档压测，记录 P50/P95/P99 与错误率

### 3.2 启动速度、错误率、崩溃频率、资源占用

【结论 / 方案】  
日志显示系统启动流程清晰，但当前仓库证据不足以形成“CPU/内存/IO 全量曲线”的定量结论；错误率方面，近 24h 落库事件 **仅 1 条 error**（熔断触发），但这不等于“无错误”，因为很多异常可能只在日志或被捕获后未落库。

【证据】  
- `logs/quant_system_20260402.log` 中存在 `ERROR | runtime_monitor | 盘中熔断触发(HARD)`  
- `runtime_incident` 近 24h：共 1 条（`monitor.circuit_breaker`，severity=error）  

【风险评估】  
- **中风险**：资源占用缺少硬指标（无进程级采样/无长期趋势），实盘无人值守时难以定位“内存泄漏/句柄泄漏/磁盘增长”。  

【优化建议】  
- 记录并落库：CPU%、RSS 内存、线程数、文件句柄数、磁盘剩余空间、分钟源请求耗时分布  
- 把“启动耗时（各阶段）”写入健康快照（scheduler/monitor/init DB 等）

### 3.3 容错能力、故障恢复与 MTBF

【结论 / 方案】  
系统具备“异常分级+告警冷却+快照落库”的基础设施，属于实盘级的必要条件；但 MTBF 目前难以稳定估计（近 24h 事件样本太少、且异常落库覆盖面有限），同时推送侧缺少统一重试队列，会削弱“故障自愈”。

【证据】  
- `src/core/runtime_monitor.py` 支持：异常分类、severity、retryable 标记、告警冷却、latency 统计、recent incidents  
- `src/modules/monitoring_store.py` 将 incident/snapshot 落库并建立索引  

【风险评估】  
- **中~高风险**：推送失败若不重试或不记录可追溯状态，实盘等同“关键通知丢失”。  

【优化建议】  
- 对推送引入“发送队列 + 重试策略 + 幂等键 + 失败落库 + 人工补发入口”  
- 对外部数据源引入“熔断/退避/缓存回退”，并把降级状态展示在看板

### 3.4 日志异常检查

【结论 / 方案】  
日志格式统一（时间|级别|模块|消息），但从 2026-04-02 的样本看，异常类目记录偏少，建议补齐关键路径的结构化日志与 trace id（便于回放）。

## 四、逻辑正确性评估

### 4.1 需求符合性（核心业务逻辑）

【结论 / 方案】  
从 README 与入口代码看，系统定位是**交易辅助（非自动下单）**，核心链路“盘前选股→盘中监控买点→推送→虚拟交易/闭环→看板展示”齐全；但测试失败表明存在若干关键逻辑未稳定满足预期。

【证据：测试结果（强证据）】  
执行 `python -m pytest -q`：  
- **124 passed / 86 skipped / 8 failed**  
- 失败用例集中在：  
  - 看板快照构建（数据聚合/编码/字段一致性）  
  - 权重配置加载（profile 一致性）  
  - 因子 IC 分析（数据依赖/表结构/数据准备）  
  - `PositionController` 市场分析依赖 `stock_daily` 表（测试 DB 缺表导致失败，暴露“依赖注入/测试隔离”不足）  
  - 二次启动盘中信号阈值（弱市/午后阈值要求未生效，导致误触发）  
  - 系统完整性保护（分钟数据为空时不应回退伪数据，但实际回退了）  

【风险评估】  
- **高风险**：盘中信号“阈值逻辑”偏差会直接影响推送准确性（误报/漏报），属于实盘级硬门槛。  
- **中风险**：市场分析/看板聚合对 DB 表结构强依赖，若环境初始化不一致会在实盘现场爆炸。  

【优化建议】  
- 以失败用例为“整改清单”，优先修复：二次启动阈值、完整性保护、看板快照一致性  
- 把“外部依赖（DB/分钟源/行情源）”抽象为可替换接口，提升测试隔离与回放能力  

### 4.2 边界条件与异常场景

【结论 / 方案】  
系统整体有异常捕获与降级，但部分路径仍会出现“隐式回退”导致逻辑不透明（例如分钟数据缺失时回退伪 intraday 数据），建议将这些行为显式化并可配置。

## 六、推送及时性评估

### 6.1 平均延迟、到达率、失败处理与重试

【结论 / 方案】  
当前推送实现是“同步 HTTP 调用企业微信 webhook”，并有 timeout 配置；但**没有看到统一的重试队列/指数退避/失败落库与补偿机制**，因此严格意义上不满足“实盘级消息可靠投递”要求。

【证据】  
- `src/modules/message_pusher.py`：一次 `requests.post()`，成功看 errcode=0，否则记录失败；异常直接返回 False  
- `src/config/config.yaml` 虽有 `position_retry_*` 等配置，但推送模块本身未体现“统一重试调度”  

【风险评估】  
- **高风险**：网络抖动或企业微信限流导致的瞬时失败，会直接丢失关键信号。  

【优化建议】  
- 以 `signal_history` 或专门 `push_outbox` 表做“待发送队列”，字段含：幂等键、payload、首次发送时间、attempt、最后错误、状态  
- 重试策略：指数退避 + 抖动（jitter）+ 最大重试次数 + 人工补发按钮（看板已具备动作入口，容易落地）  
- 推送时延统计：记录 `send_started_at / send_finished_at / response_code / errcode`，落库后就能做平均延迟与到达率评估

### 6.2 推送内容匹配度与时效性

【结论 / 方案】  
推送模板已覆盖盘前计划、盘中买卖点、持仓事件、盘后闭环摘要与系统告警，方向正确；但内容“时效性”高度依赖盘中监控轮询耗时（见稳定性部分的 97s P95 风险）。

现有报表显示“二次启动策略”在**真实触发价口径**下具备一定正收益特征，但触发率与样本稳定性仍需关注；此外回测与真实触发价口径不可直接比绝对收益，需要以统一口径、加入滑点/费用、并做样本外验证。

【优化建议】

## 八、问题清单（按风险分级与整改优先级）

### P0（必须立刻处理，否则不建议实盘）
- **凭据泄露**：`src/config/config.yaml` 明文包含 `tushare_token`、企业微信 webhook  
  - 风险：被盗用、限流、数据/推送通道被劫持  
  - 建议：改为环境变量/本地私密配置文件，历史提交做清理（至少先换 key/token）
- **盘中监控尾部时延过高**：`service.monitor_check` P95 ≈ 97s  
  - 风险：错过触发窗口，推送滞后，主循环不可预期
- **关键测试失败**：二次启动阈值与完整性保护相关用例失败  
  - 风险：误报/漏报直接影响交易决策

### P1（两周内处理，提升无人值守能力）
- **推送可靠性不足**：缺统一重试/队列/落库补偿  
- **健康心跳 stale**：部分组件只在启动打点，影响监控可信度  
- **对外部数据源依赖缺少熔断/退避统一策略**：尾部延迟与错误会扩散

### P2（持续优化，提升可维护性与可审计性）
- **资源监控缺口**：缺 CPU/内存/IO 采样与趋势  
- **评估口径波动**：多份报表触发率差异，需要版本化与统一口径  
- **静态资源外网依赖**：受限网络环境体验下降

## 九、实盘级达标判定（建议的“验收清单”）

【结论 / 方案】  
建议以可验收指标来判定“实盘级达标”，避免口头判断：

- **稳定性（SLA）**：盘中 `monitor_check` P95 < 3s，P99 < 8s；主循环无阻塞；24h 内无未恢复的 critical  
- **正确性**：核心策略/风控/推送/看板快照相关测试 **全绿**（失败=0），并补齐关键回归用例  
- **推送可靠性**：到达率（成功 errcode=0）≥ 99%；失败可追溯、可补发；平均延迟/尾延迟有统计  
- **安全**：仓库无明文 token/webhook；运行环境有最小权限；敏感配置可轮换  
- **可运维**：日志结构化、指标落库、看板可定位“慢在哪里/降级到哪一步”

## 十、附录：本次新增评估脚本

为便于你后续重复抽数，本次新增只读脚本：`tools/eval_runtime_metrics.py`，用于从 `quant_system.db` 抽取 `health_snapshot/runtime_incident` 的近 N 小时统计。
